# PayGuard environment setup

## Quick start

```bash
cp .env.example .env
# fill any VALUE_REQUIRED_FROM_USER variables (currently just PAYGUARD_DEPLOYMENT_ID)

./scripts/payguard db:start        # starts local PostgreSQL 17 (idempotent)
pnpm --filter @payguard/db migrate # applies migrations to $DATABASE_URL (payguard_dev)

anvil                              # separate terminal: local chain on :8545 (fresh state)
./scripts/payguard demo:setup      # provisions (or reuses) the local demo deployment,
                                    # prints PAYGUARD_DEPLOYMENT_ID -- put it in .env

pnpm --filter @payguard/api dev    # starts the API (apps/api, tsx watch src/main.ts)
pnpm --filter @payguard/worker dev # starts the worker (apps/worker, separate terminal)

cp apps/web/.env.example apps/web/.env
pnpm --filter @payguard/web dev    # owner control panel at http://localhost:5173
```

The API (`apps/api/src/main.ts`), worker (`apps/worker/src/main.ts`), database migrate CLI, and
`demo-setup` / `demo-reset` load the repository-root `.env` when that file exists. A variable
already set in the shell is left unchanged. `loadConfig` / `loadWorkerConfig` still read
`process.env` and fail fast on a missing or invalid required variable, naming exactly which one.

`PAYGUARD_DEPLOYMENT_ID` stays `VALUE_REQUIRED_FROM_USER` until `demo:setup` prints a real id.
Paste that id into `.env` before starting the API and worker.

`apps/web` is the owner control panel. `.env.example` sets SIWE to `http://localhost:5173`.
Open that exact origin in the browser (`127.0.0.1` will not match the SIWE domain).

On Windows, `./scripts/payguard` is bash and `db:start` expects Homebrew PostgreSQL. From
PowerShell, install PostgreSQL 17 and Foundry yourself, create the local role and databases,
then run the same `pnpm --filter ...` commands. `demo:setup` directly:

```bash
pnpm --filter @payguard/api exec tsx scripts/demo-setup.ts
```

```sql
CREATE USER payguard WITH PASSWORD 'payguard_local_dev';
CREATE DATABASE payguard_dev OWNER payguard;
CREATE DATABASE payguard_test OWNER payguard;
```

## Supabase

The API and worker talk to Postgres through `DATABASE_URL`. Supabase is that database: the
browser never receives a Supabase key. Ask for a project, then for **Project Settings → Database
→ Connection string → URI** (direct connection, or the session pooler on port 5432). Append
`?sslmode=require` and put that string in `DATABASE_URL`.

Do not use the transaction pooler (port 6543). Migrations and the worker keep a transaction
open, which that pooler does not support. Leave `DATABASE_TEST_URL` pointed at a local
`payguard_test` database. Do not run the test suite against the shared Supabase project.

`pnpm --filter @payguard/db migrate` applies `packages/db/migrations` to whatever `DATABASE_URL`
names. After it succeeds, run `demo:setup` the same way as a local database and paste the
printed `PAYGUARD_DEPLOYMENT_ID` into `.env`.

## Environment variables

| Variable | Required? | Where to get it |
| --- | --- | --- |
| `DATABASE_URL` | Yes (API + worker) | Local PostgreSQL from `./scripts/payguard db:start` — use the printed local role/db, or your own hosted PostgreSQL connection string. |
| `DATABASE_TEST_URL` | No (tests only) | Same as `DATABASE_URL` but pointed at a `payguard_test` database — only `packages/db`/`apps/{api,worker}` test suites read it. |
| `RPC_URL` | No (defaults to local Anvil) | Local `anvil` on `:8545`, or an RPC provider dashboard URL for a real network. |
| `CHAIN_ID` | No (defaults to `31337`) | Matches whatever chain `RPC_URL` actually points at. |
| `PAYGUARD_DEPLOYMENT_ID` | Yes (API + worker) | **GENERATED BY DEPLOYMENT** — printed by `./scripts/payguard demo:setup` (or `demo:reset`) after it provisions/reuses a `deployments` row. |
| `PAYGUARD_ENVIRONMENT` | No (defaults to `LOCAL_DEMO`) | One of `LOCAL_DEMO` / `TESTNET`. Keep public testnet/mainnet unselected unless separately authorized (see root `CLAUDE.md`). |
| `API_HOST` / `API_PORT` | No | Local bind address/port for the API process. |
| `API_TLS_ENABLED` | No | `true` only behind a real TLS terminator; local HTTP cookies already work over `http://127.0.0.1` (see `apps/api/src/config.ts`'s `CookieConfig` doc). |
| `API_SIWE_DOMAIN` / `API_SIWE_URI` | No | Must match the URL the frontend is actually served from once a real browser is in the loop. |
| `API_ALLOWED_ORIGINS` | No | Comma-separated CORS allowlist — the URL where the frontend is actually served. |
| `API_COOKIE_NAME` / `API_COOKIE_SECURE` / `API_COOKIE_SAMESITE` | No | Session cookie shape; leave at defaults for local dev. |
| `API_SESSION_TTL_SECONDS` / `API_CHALLENGE_TTL_SECONDS` / `API_WORKER_HEARTBEAT_STALENESS_SECONDS` | No | Timing knobs; defaults are fine locally. |
| `RELAYER_ADDRESS` | No | Optional label matching `RELAYER_PRIVATE_KEY`'s address, used only as the `from` of read-only `eth_call` simulations. |
| `RELAYER_PRIVATE_KEY` | Yes (worker) | **SECRET, LOCAL-ONLY** — a dedicated funded relayer wallet; never the owner wallet. Local default is Anvil's well-known dev account #9. |
| `WORKER_ID` | No | Defaults to a fresh random UUID per process start; set explicitly only for a stable outbox lease-owner identity across restarts. |
| `WORKER_LEASE_SECONDS` / `WORKER_POLL_INTERVAL_MS` / `WORKER_HEARTBEAT_INTERVAL_MS` / `WORKER_RECEIPT_POLL_ATTEMPTS` / `WORKER_RECEIPT_POLL_INTERVAL_MS` / `WORKER_INDEXER_BATCH_BLOCKS` | No | Worker timing/batching knobs; defaults are fine locally. |
| `PAYGUARD_DEMO_ENABLED` | No | `true` to turn on the B2 demo bridge (`/v1/demo/*`) and require the three demo keys below. |
| `PAYGUARD_DEMO_INSTANCE_LABEL` | No | Defaults to `payguard-local-demo`; the idempotency label `demo:setup`/`demo:reset` provision under. |
| `DEMO_AGENT_PRIVATE_KEY` / `DEMO_MERCHANT_PRIVATE_KEY` / `DEMO_UNAUTHORIZED_MERCHANT_PRIVATE_KEY` | Yes if `PAYGUARD_DEMO_ENABLED=true` | **SECRET, LOCAL-ONLY** — isolated demo actor keys, never the owner key. Local defaults are Anvil well-known dev accounts #1, #2, and #9. |
| `PAYGUARD_DEMO_RESET_CONFIRM` | No | Set to the literal `yes` only when deliberately running `demo-reset.ts`'s destructive redeploy — leave unset otherwise. |

**Uniswap v4 / Aqua-SwapVM:** no separate env vars. Pool/adapter/router/strategy identities are
provisioned by `demo:setup`/`demo:reset` and stored in PostgreSQL (`deployments`/`vaults`/
`policies`), not read from the environment — see `docs/implementation/B2_BACKEND_HANDOFF.md`.

**Optional features:** fee subsidy is NOT_SELECTED for the required MVP gates (root `CLAUDE.md`)
— there is no env var for it because no code path reads one.

## Owner keys

Neither the API nor the worker will boot if `OWNER_PRIVATE_KEY`, `VAULT_OWNER_PRIVATE_KEY`,
`OWNER_KEY`, or `OWNER_MNEMONIC` is set at all — `assertNoOwnerKeyConfigured` in both
`apps/api/src/config.ts` and `apps/worker/src/config.ts` refuses to start. The owner's key exists
only inside `apps/api/scripts/demo-setup.ts`/`demo-reset.ts` (operator scripts that exit after
provisioning), never in a running process.

## Local vs production shape

`.env` is gitignored (`.gitignore` lines 42–45); `.env.example` and `.env.*.example` are the only
committed templates. Every value in `.env.example` is a disposable local-only default or a
`VALUE_REQUIRED_FROM_USER` placeholder — none may hold a real credential. Before any non-local
deployment, `API_TLS_ENABLED`, `API_COOKIE_SECURE`, `API_ALLOWED_ORIGINS`, `PAYGUARD_ENVIRONMENT`,
`RELAYER_PRIVATE_KEY`, and the three `DEMO_*_PRIVATE_KEY` variables all need real reconsideration
— none of the current defaults are production-safe as-is.
